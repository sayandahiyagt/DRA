# ADR-021 — §38.4 verification-gate contract: pure queries over the 0002 schema

- **Decision type:** Evidence-driven PD
- **Confidence:** Medium-high (contract defined; gate predicate implemented in-process, schema expressible as queries, not yet exercised against adversarial fixtures — that is the §38.4 proof and the gate-test parts of dra#8)
- **Status:** Accepted
- **Spec anchor:** §38.4 verification-gate proof (line 2655); §20.2 verification layers (line 1487); §20.3 verification outcome (line 1526); §20.4 anti-citation-laundering (line 1539); §21.1 staged vs canonical state (line 1549); §14 invalidation and freshness (line 1159); §14.2 dependency-based invalidation (line 1189); §29 / §27.5 UGC poisoning defenses (line 2060 / 2108); §22 access-basis record (line 1625); ADR-007 verification gate (line 191); ADR-004 versioned/staleness-aware artifacts (line 172); ADR-013 transactional publication (line 229); ADR-015 source-access policy (line 243).
- **Evidence:** §38.4 constructs adversarial fixtures (correct primary source + misleading secondary; two derivative sources presenting the same false claim; stale docs vs current behavior; parser-corrupted equation; prompt-injection page; issue/forum claim contradicted by code/tests). The gate passes only if unsupported confidence falls and contradictions remain visible. Deep-research evaluation shows citation presence/relevance is insufficient for factual support and misleading evidence can strongly alter results [R6][R7]; cheaper rubric models can be competitive as calibrated LLM judges, but evaluator biases still require calibration [R22]. The dra#14 canonical schema (`alembic/versions/0002_evidence_schema.py`) already carries every column the gate needs; `prov_derivation` recursive walks are proven by `tests/test_provenance_traversal.py` with both-direction indexes (`ix_prov_derivation_source`, `ix_prov_derivation_derived`, `ix_prov_derivation_activity`). `tests/test_schema_introspection.py` asserts a fixed canonical table/enum surface and does not include the standalone `proof_corpus` added in `0003` — a deliberate contract.
- **Decision:** The §38.4 gate is **pure queries over the existing 0002 tables** plus an **indexes-only** `0004` migration (`ix_claim_verification_state` GIN on `claim.verification_state`; `ix_derived_artifact_staleness` on `derived_artifact(state, valid_to)`). No new canonical table or enum is introduced, so `test_schema_introspection` is not touched. The gate contract has four rules:

  1. **Gate-pass criterion (unsupported-confidence-falls).** A `claim` passes the gate only when its `claim.confidence` is supported by evidence that satisfies the applicable per-source verification policy; a claim whose confidence exceeds its supporting evidence (or fails the deterministic entailment predicate) does **not** pass. Pass/fail and the supporting evidence IDs are recorded in `claim.verification_state` JSONB (see `verification_state` columns on `claim`).

  2. **Contradictions stay visible.** Contradictions are never resolved away by the gate. Evidence-level contradictions are recorded as `claim.verification_state->'contradictions'[]` (the IDs of contradicting evidence); topic-level contradictions surface via `topic_relationship(relationship_type='contradicts')`. A contradicting edge must be present and visible for the gate to report its verdict — visibility is a precondition of the verdict, not a side effect.

  3. **Derivative-masquerade rule (anti-citation-laundering, §20.4).** Two supporting sources are treated as **independent corroboration** only when a recursive `prov_derivation` lineage walk does **not** reach a shared upstream source from both. The gate walks `prov_derivation(derived_entity_id, source_entity_id, activity_id)` backward from each supporting evidence entity toward `raw_capture`; if the two walks intersect a common source lineage, the sources are derivative of one another and are collapsed into a single evidence weight rather than counted twice. If they share no lineage they may count as independent. This is the Layer 5 independence check (§20.2); the recursive CTE primitive and both-direction indexes are already present in `0002`.

  4. **Freshness / quarantine rule (staleness propagation, §14 / §21.1).** `derived_artifact.staleness_policy` (JSONB) drives downstream state: when a derived artifact is `stale`/`rejected`/`superseded` (`evidence_state`), dependents — `evidence_unit` → `claim` → `decision`/`handoff_statement` — must not silently count as current. The gate quarantines any claim whose supporting evidence chain reaches a `stale`/`rejected` artifact and requires revalidation (`valid_from`/`valid_to`) when freshness matters (§14.1 signals; ADR-004 versioning). Only `CANONICAL`+`VERIFIED` evidence (`evidence_state`) may carry a high-impact claim to gate pass. Per §21.1, only `CANONICAL` or stronger records may support synthesis.

  5. **Per-source evidence-rule boundary (prompt-injection / UGC, §27.5 / §29).** Retrieved content is untrusted data at a hard trust boundary (§29). The gate enforces a per-source boundary keyed on `source_identity.access_basis` (ADR-015): UGC/user-provided and prompt-injection-bearing captures are quarantined from redefinining system instructions, granting tool permissions, or requesting credentials (§27.2/§27.4), cap duplicate/derivative evidentiary weight and require independent corroboration for high-impact UGC-derived claims, and track source lineage/domain frequency so a single user-generated source cannot concentrate disproportionate influence [R8].
- **Why chosen / Alternatives:** A dedicated `verification_result` table was considered for first-class auditability. It was rejected for this cycle because it would (a) force a coupled edit to `tests/test_schema_introspection.py`'s fixed `EXPECTED_TABLES`/`EXPECTED_ENUMS` contract — exactly the coupling `0003` avoided for `proof_corpus` — and (b) duplicate state already expressible in `claim.verification_state` JSONB plus `topic_relationship`. The gate's per-fixture predicate is an in-process judge over rows (spec §20.3 / Layer 3 entailment), which is pure runtime logic, not schema. Lineage walks reuse the already-proven `prov_derivation` recursive CTE. Thus every gate concern maps to an existing 0002 column, and `0004` adds only the two indexes that accelerate the gate's JSONB predicates and staleness scans — `prov_derivation` lineage-walk indexes are already present, so none are added.
- **Reversal trigger:** This decision is reversed (and `0004` re-opened to add a `verification_result` table, extending `test_schema_introspection` in the same wave) if any of the falsifiable §38.4 gate proofs fail: (1) a derivative-masquerading claim passes the gate (two derivative sources counted as independent corroboration); (2) a real contradiction is not surfaced in `claim.verification_state->'contradictions'[]` or `topic_relationship(reltype='contradicts')`; or (3) a stale/rejected `derived_artifact` supports a gate-passing claim without quarantine. Operationally, reversal also triggers if the pure-query predicate cannot be expressed within the 0002 column set and a persistent audit relation becomes required.
- **Consequences:**
  - Positive: the §38.4 gate is fully queryable over the existing canonical schema; later gate-test parts (dra#8 parts 2–4) consume `dra.db.engine` + `tests/_db.py` with no second `DATABASE_URL`, and `test_schema_introspection` stays green without edits. The GIN/`staleness` indexes accelerate the JSONB predicates and freshness scans the gate issues.
  - Risk/neutral: the deterministic entailment predicate is in-process (spec §20.3) and is exercised by the §38.4 adversarial fixtures in the gate-test parts, not by this migration; its calibration (false-positive/false-negative rates, [R22]) is a follow-on measurement. Gate verdicts live in `claim.verification_state` JSONB rather than a dedicated table, which is sufficient for v1 but means ad-hoc audit queries against a normalized `verification_result` relation would need the heavier alternative above if auditability hardens into a requirement.
